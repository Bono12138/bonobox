# 测试报告

## 结论

版本：Portable Search MCP 2.1.0<br/>
测试日期：2026-08-05<br/>
环境：Windows、Python 3.13.3、`ddgs 9.14.4`、`pytest 9.0.2`<br/>
商业搜索 API Key：未配置、未传入

最终基准覆盖 30 个公开场景、3 轮、90 次真实联网请求。90/90 请求成功；网页和图片 66/66 轮有结果；新闻 24/24 轮有结果且日期完整率为 100%；普通语句官网导航 16/18 轮进入前 5，明确 `site:` 后 18/18 排在第 1 位。P50 为 2.537 秒，P95 为 9.055 秒。

这些数据证明当前版本可用于 Agent 的公开信息检索、图片候选发现、带日期的新闻搜索和限定来源检索。它仍没有长期稳定性、固定排序、固定配额或服务等级保证。

## 真实联网测试

命令：

```powershell
$env:RUN_LIVE_SEARCH_TESTS='1'
python -m pytest -q tests\test_live_search.py
```

该组测试覆盖英文网页、中文网页、图片和近一天新闻。网页、图片必须返回公开 URL；新闻返回项必须全部具有可解析时间，并满足本地时间窗口。

## 表现问题与修复

### 1. 普通官网导航

2.0.1 的 33 次基准中，3 个普通官网任务运行 3 轮，只有 4/9 轮把目标域名排进前 5。原因包括候选池过小、免费后端选择波动，以及搜索引擎把百科或相关文章排在官网之前。

2.1.0 做了以下处理：

- 官网意图只在内部扩大到 10 个候选，最终仍按用户要求返回结果数；
- 将“官方网站、官网、official documentation”等写法规范化后再搜索；
- 对机构名称与标题、域名关键词和政府域名进行重排；
- 降低 Wikipedia、Wikidata 作为官网导航结果的优先级；
- 中文官方站点在低置信情况下追加 `site:gov.cn` 查询；
- `ddgs` 单后端超时设为 3 秒，限制慢请求的等待成本。

最终 6 个普通官网任务运行 3 轮，16/18 轮进入前 5；两次漏检均为人民银行官网。相同目标使用明确 `site:` 查询时，18/18 排在第 1 位。工具因此继续建议：要求确定官网时必须写明目标域名。

针对剩余漏检，另用同一条人民银行官网查询分别探测 Bing、Brave、DuckDuckGo、Google、Mojeek 和 Yahoo：本轮只有 Bing 返回候选，但候选中仍没有人民银行官网，其余后端没有返回结果。进一步尝试“官方”“官方网站”和带引号的“官网”写法，也没有形成稳定命中。剩余问题位于免费上游的候选召回阶段，结果重排无法补回上游未返回的 URL。

没有为单个测试目标写死“机构名称 → 官网域名”映射。这类字典会过期，也无法覆盖任意机构，容易把旧域名错误地包装成确定答案。当前通用且可验证的处理仍是：已知目标域名时使用 `site:目标域名`；未知域名时把普通搜索结果当候选，并打开原页核验。

### 2. 新闻覆盖与时效

2.0.1 的新闻查询只有 3/6 轮得到合格当天结果，另有上游异常。单纯增加重试虽然把部分查询救回，但 P95 一度上升到 17.862 秒。

2.1.0 改为：

- 优先查询带 `pubDate` 的公开 Google News RSS；
- RSS 失败或没有合格结果时，再调用 Bing、DuckDuckGo 和 Yahoo 新闻后端；
- 中文新闻失败时允许地区回退，但限制重试次数；
- 支持 RFC 2822、ISO 和英文相对时间；
- 所有结果继续执行本地日期过滤，过期或无法解析日期的结果不会用于补数。

最终 8 个新闻场景运行 3 轮，共 24/24 轮有结果；所有返回新闻都有可解析日期，日期完整率为 100%。RSS 结果可能使用新闻聚合跳转 URL，重要结论仍需打开原文核对。

### 3. Windows 标准输入输出编码

全新 ZIP 测试曾在系统默认 CP936 时触发 UTF-8 解码失败。入口现在明确将标准输入、标准输出和标准错误配置为 UTF-8，并有独立回归测试。MCP 消息中的中文请求 ID 已在非 UTF-8 默认环境下验证通过。

## 最终 90 次基准

基准包含 18 个网页、4 个图片和 8 个新闻场景；其中 6 组普通官网与 6 组 `site:` 官网形成对照。中英文均有覆盖。每个场景连续运行 3 轮，每轮最多返回 5 条。

命令：

```powershell
$env:PYTHONPATH=(Get-Location).Path
python scripts\benchmark_search.py --rounds 3 --max-results 5 --output docs\benchmark-2026-08-05-v3.json
```

| 指标 | 最终结果 |
|---|---:|
| 请求成功率 | **90/90（100%）** |
| 网页/图片有结果率 | **66/66（100%）** |
| 普通官网进入前 1 | **13/18（72.2%）** |
| 普通官网进入前 3 | **16/18（88.9%）** |
| 普通官网进入前 5 | **16/18（88.9%）** |
| `site:` 官网排在第 1 位 | **18/18（100%）** |
| 新闻有结果率 | **24/24（100%）** |
| 新闻日期完整率 | **100%** |
| URL 有效率 | **100%** |
| 单次结果去重率 | **100%** |
| 响应时间 | **P50 2.537 秒；P95 9.055 秒** |
| 单次返回结果数中位数 | **5 条** |

最终逐轮数据见 [`benchmark-2026-08-05-v3.json`](benchmark-2026-08-05-v3.json)。脚本只保存公开查询、耗时、结果数、域名、日期计数和状态，不保存标题、摘要或网页正文。

## 与 2.0.1 同场景对比

将最终实现限制到 2.0.1 使用的同一批 11 个场景、33 次请求后：

| 指标 | 2.0.1 | 2.1.0 同场景 |
|---|---:|---:|
| 请求成功 | 31/33 | **33/33** |
| 网页/图片有结果 | 27/27 | **27/27** |
| 普通官网进入前 5 | 4/9 | **7/9** |
| `site:` 官网进入前 5 | 9/9 | **9/9** |
| 新闻有结果 | 3/6 | **6/6** |
| P50 | 2.244 秒 | 3.228 秒 |
| P95 | 4.618 秒 | 6.931 秒 |

覆盖率和官网命中率提高，但规范化查询和回退增加了部分请求的耗时。最终扩大到 90 次后的 P50 为 2.537 秒，P95 为 9.055 秒。该延迟成本需要在使用说明中保留，不能用平均值代替。

## 尚未证明的能力

- 长期、高并发或批量稳定性；
- 任何公开后端的固定配额、固定排序或跨地区一致性；
- 分钟级实时新闻，以及上游发布时间字段绝对真实；
- 网页正文抓取、付费墙、登录后页面和企业内部资料；
- 搜索摘要足以单独支撑医疗、法律、财务、审计等高风险结论。

原始数据只代表测试时点、网络出口和当时可用后端，不构成未来承诺。
